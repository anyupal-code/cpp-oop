## 2.1. RAII

**Задание 1.** Напишите класс `File`, который открывает файл
в конструкторе и закрывает в деструкторе. Убедитесь, что при выходе
из блока файл закрывается.

**Ответ.**

```cpp
#include <cstdio>
#include <stdexcept>

class File {
    std::FILE* f_ = nullptr;
public:
    explicit File(const char* path) : f_(std::fopen(path, "r")) {
        if (!f_) throw std::runtime_error("cannot open file");
    }
    ~File() { if (f_) std::fclose(f_); }
    std::FILE* get() const { return f_; }
};

int main() {
    {
        File f("data.txt");
        // ... чтение ...
    }   // здесь сработал деструктор, файл закрыт
}
```

**Задание 2.** Что произойдёт, если внутри блока после создания `File`
выбросить исключение?

**Ответ.** При раскрутке стека деструктор `File` всё равно вызовется —
ресурс освободится. В этом и смысл RAII: не нужно писать `close`
на каждой ветке выхода.

**Задание 3.** Почему `File` нельзя копировать «как есть»?

**Ответ.** Копия по умолчанию скопирует указатель `f_`, и оба объекта
попытаются закрыть один и тот же файл — двойное освобождение. Либо
глубокое копирование, либо `= delete`.

## 2.2. Правило трёх / пяти

**Задание 1.** Дан класс `Buffer` с полем `int* data_`. Какие методы
нужно определить, чтобы правило трёх выполнялось?

**Ответ.** Деструктор (`delete[] data_`), конструктор копирования
(выделить новый массив и скопировать), оператор присваивания
копированием (освободить старый, выделить новый, скопировать).

**Задание 2.** Почему в операторе присваивания проверяют
`if (this != &o)`?

**Ответ.** При самоприсваивании (`a = a`) без проверки мы освободим
`data_`, а затем попытаемся скопировать из уже освобождённой памяти.
Проверка предотвращает этот случай.

**Задание 3.** Что добавляют к правилу трёх, чтобы получить правило
пяти?

**Ответ.** Конструктор перемещения и оператор присваивания
перемещением. Они забирают ресурс у временного объекта, не копируя.

**Задание 4.** Как запретить копирование класса `Buffer`?

**Ответ.**

```cpp
Buffer(const Buffer&)            = delete;
Buffer& operator=(const Buffer&) = delete;
```

## 2.3. Умные указатели

**Задание 1.** Чем `unique_ptr` отличается от `shared_ptr`?

**Ответ.** `unique_ptr` — единоличное владение, не копируется,
только перемещается. `shared_ptr` — совместное владение через счётчик
ссылок, освобождает ресурс, когда счётчик станет нулём.

**Задание 2.** Почему `unique_ptr` нельзя скопировать, но можно
переместить?

**Ответ.** Копирование создало бы второго владельца, и было бы
непонятно, кто освобождает ресурс. Перемещение явно передаёт владение:
старый `unique_ptr` становится пустым, новый — владеет.

**Задание 3.** Зачем нужен `weak_ptr`?

**Ответ.** Чтобы ссылаться на объект под `shared_ptr`, не увеличивая
счётчик ссылок. Основной сценарий — разрыв циклических зависимостей
(иначе счётчики никогда не дойдут до нуля, и объекты не освободятся).

**Задание 4.** Какой умный указатель выбирать по умолчанию?

**Ответ.** `unique_ptr`. `shared_ptr` — только если владение
действительно общее.

## 2.4. Исключения

**Задание 1.** Напишите функцию, которая выбрасывает
`std::runtime_error`, и перехватите её в `main`.

**Ответ.**

```cpp
#include <iostream>
#include <stdexcept>

void fail() { throw std::runtime_error("something failed"); }

int main() {
    try {
        fail();
    } catch (const std::exception& e) {
        std::cout << "error: " << e.what() << "\n";
    }
}
```

**Задание 2.** Почему ловят по `const std::exception&`, а не по
`std::exception` (без ссылки)?

**Ответ.** При ловле по значению наследник (например,
`std::runtime_error`) «срежется» до `std::exception`, и информация
о конкретном типе потеряется. Ссылка сохраняет полиморфизм и
позволяет вызвать правильный `what()`.

**Задание 3.** Что произойдёт с локальными объектами в блоке `try`,
если выброшено исключение?

**Ответ.** При раскрутке стека для всех полностью созданных локальных
объектов вызовутся деструкторы. Ресурсы освободятся (RAII работает
и при исключениях).
